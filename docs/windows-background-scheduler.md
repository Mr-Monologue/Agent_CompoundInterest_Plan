# Windows 独立后台调度：v0.32.0 上线与回滚预案

本文件是部署预案，不表示生产已经切换。新代码先通过 feature → develop 的审查和 Ubuntu/Windows CI；生产仍为 v0.31.8。生产升级、0037 迁移及来源切换必须另获本版本的明确确认。

## 当前值与拟议值

| 项目 | 当前 | 拟议 |
|---|---|---|
| 每日行情同步、风险扫描、健康检查 | Hermes 来源，调度推进异常 | Windows 计划任务唤醒独立 HTTP 工作进程 |
| 业务时间、时区、启用状态、参数、最大重试次数 | Core 已批准自动化政策 | 原值不变，每次执行前复核 |
| 其他 Hermes 任务与交互能力 | 原配置 | 保留 |
| 通知 | Core outbox + Hermes 投递/回执 | 本轮不迁移投递，执行成功不等于送达 |
| 财务事实 | 既有策略、持仓、现金、交易、计划 | 不变 |

## 执行契约

- Windows 只负责每分钟唤醒，不复制每日业务时刻。工作进程只通过回环 HTTP 读取 Core 政策并请求执行，不打开 Hermes、Codex，不直接读取投资账本。
- Core 在同一个 `BEGIN IMMEDIATE` 事务中检查来源、策略版本并领取任务。并发请求只能有一个领取者；成功、降级、跳过或仍在运行的任务均返回原记录。来源代际隔离旧 Windows 进程；无代际的 Hermes 请求在 Windows 接管期间被拒绝，包括原有 catch-up/retry 入口。
- 切换/停用/回滚均为预览 → 15 分钟有效草稿 → 明确确认 → 原子提交。策略或来源变化必须重新预览；存在 RUNNING 的首批任务时拒绝切换。全部首批任务一起切换，每项任务仅一个可接受来源。
- 每次切换建立新的起始边界；边界以前的任务禁止自动执行。当前漏跑检测结果归档为人工核查记录。不会将漏跑写成成功，回滚也不补旧积压。
- 休眠/关机时不唤醒设备。恢复后逐个补跑切换以来、批准之后且在 24 小时内的应执行时刻。更早的记录为 EXPIRED；超过 7 天的离线区间额外记录 MISSED_RANGE，最近 7 天逐次列出。记录 `scheduled_for` 与 `actual_at`，Core 同时保留 `started_at`。
- Core 业务失败沿用原任务次数与退避（5/15/30/60/120 分钟），上限取批准政策。HTTP/连接失败另记本地持久日志，按同一政策次数上限退避。达到上限后需要人工核查，不因重启再次重试。每分钟只读连通性探测可持续进行。
- 响应丢失后用同一应执行时刻请求，Core 返回既有结果。若 Core 进程在业务处理中崩溃，RUNNING 事实保留、标记需核查，不自动重放可能已发生的副作用。这是保守防重复，不承诺任意外部副作用的 exactly-once。
- 工作台显示首批来源、收到的心跳、各政策下次时间和异常；其他 Hermes 调度快照仍单独保留，不把新进程健康当成全部 Hermes 任务正常。
- 本地 journal 保留失败/过期证据。恢复连通后上传摘要；未确认的历史异常会持续显示。生产日志轮转、异常人工核销和独立通知渠道属于后续运维能力。

## 历史保护清单

用户指定的三次历史漏跑应保留本机只读证据，不将具体生产记录提交到源码仓库。禁止重试、改成 SUCCESS 或用本轮测试数据替代。切换边界将覆盖这些历史时刻；部署验收须与用户已核对的记录逐一比对。

## 审批后部署步骤（本轮不执行）

1. 完成源码审查及 Ubuntu/Windows CI；依长期分支规则发布明确版本。取得 Ryan 对 v0.32.0 升级、数据库迁移和首批三任务切换的确认。
2. 在生产运行目录使用现有更新流程备份数据库、配置、Core 任务 XML 和版本。备份必须从生产目录执行，防止相对数据库路径指向开发仓库。独立保存新 worker journal（若已有）。备份须验证可读。
3. 按已有升级流程安装审查通过的版本并迁移到 0037；不启动 Hermes、不触发业务同步。核对 `/health`、`/ready`。预期升级默认来源仍为 HERMES，不会自动接管。
4. 预览（GET-only）：

   ```powershell
   .\runtime\windows\manage-background-scheduler.ps1 -ProjectRoot C:\investor\value-dca-agent -Action Preview
   ```

5. 安装独立任务，保持禁用：同一脚本 `-Action Install -Apply`。已有同名任务时拒绝覆盖，先人工审查。任务使用当前运行账户的 S4U、Limited 权限、AtStartup + 每分钟唤醒、StartWhenAvailable、IgnoreNew；不要求交互聊天。部署账户必须拥有该运行目录与本地 journal 的访问权和注册任务权限。
6. 切换：`-Action Switch -Apply`。脚本再次展示政策和来源，输入“确认”后提交短期草稿，再启用并启动新任务。确认令牌仅存内存。Core 原子校验是防双来源的最终关卡：Hermes 即便恢复，也无法执行这三项；不需要删除整个 Hermes 配置。可在后续单独授权中停用那三条旧唤醒，避免拒绝日志噪声。
7. 验收：新心跳、政策下次时刻、第一次真实应执行记录的来源/应执行/实际时间、通知 outbox 与真实回执分别检查。不开 Codex/Hermes 的实际整晚运行和真实休眠/重启，属于上线观察，不能以单元测试替代。

Core 必须由现有受管任务提供 HTTP 服务。若 Core 只在用户登录后启动，则开机未登录期间 worker 会记录 Core 离线，等 Core 恢复后按窗口补跑；本脚本不擅自改 Core 服务账户或登录方式。若要求开机未登录也完成任务，应在上线前另行验证/配置 Core 的启动方式。S4U worker 不依赖远程凭据，实际行情请求由 Core 执行。

## 停用与回滚

- 停用预览：`-Action Pause`；确认执行用 `-Action Pause -Apply`。先在 Core 切为 PAUSED，再禁用/停止 Windows 唤醒；三个任务都不执行，其他 Hermes 功能不变。
- 回滚预览：`-Action Rollback`；确认执行用 `-Action Rollback -Apply`。先将来源切为 HERMES、使旧 Windows 代际失效，再禁用新任务。Hermes 进程本身不会由脚本擅自启动；应单独核对其真实心跳。历史积压不重放。
- 若任务启用失败而 Core 已接管：不要绕过来源校验，查看工作台心跳异常并按回滚流程处理。Core 不可用时禁止伪造切换成功；可以先人工禁用新任务止损，待 Core 恢复完成受控回滚。
- 优先回滚调度来源而不是数据库。禁止在仍有生产新事实时盲目恢复旧数据库。若必须恢复 v0.31.8，先停用新工作进程、经确认回滚来源、保全新记录，再按已有恢复方案评估备份与差异；迁移降级仅在隔离环境验证，不作为自动生产脚本。

## 验证分类

- 自动化：并发领取、重复请求、丢失响应、业务失败/退避、传输失败上限、重启日志恢复、补跑窗口、长关机区间、策略漂移、启停回滚、心跳异常、HTTP 草稿确认与任务作用域。
- 隔离进程实测：临时 SQLite、随机本机端口、真实 Uvicorn Core 与独立 worker 进程、SYSTEM_DOCTOR 执行、重复运行和 Core 停止后的离线记录；政策批准时刻为合成数据。无真实行情或生产财务写入。
- 待上线：计划任务账户/S4U 权限、无聊天整夜运行、真实休眠/断电恢复、Core 系统启动能力及通知到达。未验证项保持待验收。
