# D1 现有持仓比较与复核

## 相对既有能力新增什么

复用原基准分段、日序列/披露窗口、MAPER、版本论点及决策日志，不重新计算一套收益，不建立总分。新增逐原因可追溯依据、比较资格、固定输入指纹、不可变复核快照、证据版本待办和追加处理记录。

“复核我的持仓”用 `investor-assistant holdings-review`。查询只读，范围为该组合账户实际正份额持仓；未保存基线显示“尚无保存的复核基线”，不能将上次查询冒充已完成复核。“查看复核处理历史”用 `review-history`。原 `review` 仍为研究摘要。

## 比较边界与证据

每只仅与自己对应时期基准比较；统一排名为空、跨产品排名资格为否。登记名称、原文投资范围与正式产品分类分开：只有已引用原文含明确类型才展示披露标签，无法结构化的类型列缺口，不从名称猜正式分类。标签不构成同类资格。官方比较基准与诊断映射、历史有效期、权重/币种/收益口径均保留；未批准映射为候选，不进入正式风险动作。

原因类别顺序是复核工作性质，不是买卖或风险分数：先核对证据差异；复核已观察结果；待配置确认；仅缺证据；背景事实。WARNING本身不创建统一紧急级别。费用/集中度引用现有带日期和来源的MAPER原文，不解析成未经验证的指标或把历史结构当实时值；缺失不记零。

窗口负差额只表示该窗口落后，正负窗口并存表示端点敏感；不称选股Alpha。回撤只沿用“基金最大回撤（共同交易日）”，无日序列显示缺失；不把累计亏损当回撤。管理人公布路径不称独立成分重建。净值已体现内部费用，不再次扣除。未来结束的窗口不显示为当前已知结果。

## 保存与处理

1. GET `/v1/holding-review` 只生成原因和待办建议。每原因有稳定原因标识、证据版本、日期、来源指纹、输入计算记录与口径，客户端代管技术标识。
2. 用户表达保存复核意图后，命名工作流 `review-capture` 调用 POST `/v1/holding-review-captures`，带当前输入指纹。保存时再核对；变化须重读。相同输入复用快照，相同原因和证据版本复用待办；新证据或内容追加新记录并链接旧待办，不覆盖历史。查询不会自动保存。
3. `review-handle` 调用 POST `/v1/holding-review-tasks/{id}/handling`，记录补证请求、暂缓或“已复核但保留限制”。要求说明和当前处理版本；可引用同基金证据。处理仅表明人已阅读/采取研究步骤，不证明问题消失，不能暗中批准论点/映射、改资金规则或产生交易。
4. 固定请求键复用现有客户端响应丢失保护；未知响应先GET历史核对，不能换键盲重发。并发保存/处理在事务内核对，重复请求原样返回。
5. 历史端点保留完整快照、来源、规则版本和处理记录；展示的“相对上次”是最后一次明确保存的复核输入。保存时点与数据日分开。旧快照是当时已知输入，不用今天批准状态重算历史，不提供伪造历史回放。

三个新增表仅存研究快照/待办/事件；不接入策略、计划、风险执行或账本。具体论点/映射仍走独立内容确认。生产本轮仅查询与预览，使用真实归档备份在隔离回环HTTP中验证保存与处理，不为验收制造生产待办完成记录。
